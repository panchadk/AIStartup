Step 2: chunk_text

Pack whole paragraphs into a chunk until the next one would not fit. A paragraph that is longer than the limit on its own is first preceded by closing the chunk in progress, then cut by words. Keeping paragraphs together matters: a passage cut in half makes both halves harder to find.

def chunk_text(text, max_words=60):
    chunks, current, count = [], [], 0
    for para in [p.strip() for p in text.split("\n\n") if p.strip()]:
        words = para.split()
        if len(words) > max_words:
            if current:
                chunks.append("\n\n".join(current)); current, count = [], 0
            for i in range(0, len(words), max_words):
                chunks.append(" ".join(words[i:i + max_words]))
            continue
        if count + len(words) > max_words and current:
            chunks.append("\n\n".join(current)); current, count = [], 0
        current.append(para); count += len(words)
    if current:
        chunks.append("\n\n".join(current))
    return chunks

Step 4: cosine_scores

The dot product of the query with every row, divided by the product of the lengths. The tiny number 1e-12 avoids dividing by zero for an all-zero vector. Because it divides by the lengths, the result does not change if you scale a vector, which is what makes it a measure of direction.

def cosine_scores(query_vec, matrix):
    dots = matrix @ query_vec
    norms = np.linalg.norm(matrix, axis=1) * np.linalg.norm(query_vec)
    return dots / (norms + 1e-12)

Step 5: top_k

np.argsort sorts from lowest to highest, so reverse it with [::-1] and take the first k. Slicing with [:k] already handles a k that is larger than the number of rows.

def top_k(query_vec, matrix, k=3):
    scores = cosine_scores(query_vec, matrix)
    order = np.argsort(scores)[::-1][:k]
    return order, scores[order]

Step 6: evaluate_search

For each query, retrieve the top k chunks, join their text, and see whether any gold phrase appears. Lowercase both sides so capital letters do not matter. A query counts as a hit if any gold phrase is found.

def evaluate_search(eval_set, texts, embs, embed_fn, k=3):
    hits, missed = 0, []
    for item in eval_set:
        idx, _ = top_k(embed_fn([item["query"]])[0], embs, k)
        retrieved = " ".join(texts[i] for i in idx).lower()
        if any(g.lower() in retrieved for g in item["gold"]):
            hits += 1
        else:
            missed.append(item["query"])
    return hits, missed

If you are stuck below 15 of 20

Print the missed queries and look at each one with show(query). Almost every miss has one of these causes:

  1. The gold phrase is too narrow. The search returned a perfectly good passage that simply does not contain your phrase. Widen the gold list, for example by adding a second name that the answer may use.
  2. The answer is not in your documents. Replace the query, or add the missing content.
  3. The chunk is the wrong size. Compare sizes at the same text budget, as in Step 7. If your paragraphs are very long, smaller chunk sizes help; if they are very short and fragmentary, larger sizes help.
  4. Your query shares no words with the answer and the topic is rare. Embedding models know common language better than rare jargon. Try rephrasing the query the way a user would, or add the jargon term to the passage text.
  5. The paragraph breaks are missing. If your files are one long block of text, the chunker has no paragraphs to keep together and cuts every N words. Add blank lines between paragraphs.

Sample answers to the written questions

  • Rephrasing experiment: a good answer reports a question that worked even though it shared no words with the passage (semantic search at work), and one that failed, with a guess about why (rare jargon, a very general question, or the answer being split across passages).
  • Which chunk size was best and why: smaller chunks tend to win at an equal text budget on documents made of short, separate passages, because a focused chunk matches a focused question. Larger chunks help when the answer needs surrounding context. With longer paragraphs, the best size usually moves up. The exact winner depends on your documents, so say what you measured.
  • Stretch, re-ranking: a cross-encoder usually improves the order within the top candidates, which helps most when the right passage is retrieved but not in the top 3. It costs more time per query, because it must read each candidate together with the question.

Common mistakes and what they look like

  • Test queries that copy words from the document: the score is high, but it measures keyword matching, not meaning. Write queries the way a real user would ask.
  • Gold phrases that also appear in the query: the self-check rejects these, because they make the test trivial.
  • Comparing chunk sizes with the same k: bigger chunks return more text and look better by luck. Use an equal text budget.
  • Sorting scores the wrong way: results come back worst first. np.argsort sorts ascending.
  • Dot product instead of cosine for unnormalized vectors: long vectors dominate the ranking regardless of meaning.
  • Forgetting to re-embed after changing the chunk size: the chunk list and the embedding matrix no longer match, so results point at the wrong text. Use build_index, which does both together.
  • Judging by a few handpicked queries: it feels fine and hides failures. Use the 20-query test set.
