1. The big picture

You have a task and a language model that does not do it well yet. There are three ways to close the gap:

  1. Prompt it better: write clear instructions and show worked examples. Nothing is trained.
  2. Retrieve for it (RAG): look up the facts it lacks and put them in the prompt (Module 7).
  3. Fine-tune it: train the model itself on examples of the behaviour you want.

Beginners reach for fine-tuning first because it sounds powerful. Experienced teams reach for it last, because it costs data, time, money and maintenance. This module teaches you to decide with numbers rather than with excitement.

2. The decision ladder

  • Rung 1, prompt. Often enough. It is free to try and instantly changeable.
  • Rung 2, few-shot. Show 3 to 10 worked examples in the prompt. This fixes many format problems.
  • Missing facts? Use RAG. Facts change, and a model's weights are a bad place to store them.
  • Missing consistency, style, speed or low cost? Now fine-tuning is worth considering: the behaviour is built into the model, so the prompt can be short.

3. What fine-tuning changes

Fine-tuning changes the model's habits: the format it answers in, the tone it uses, the way it handles one narrow type of input. It is much less good at teaching new facts, and the facts go stale.

Good candidates are narrow, repeated tasks with a stable definition of "right":

  • Extracting fields from messages into JSON.
  • Classifying tickets, emails or reviews into your own categories.
  • Rewriting text in a fixed house style.
  • Following a long set of rules that you do not want to resend in every prompt.

The practical benefits: consistent format (no chatter around the JSON), shorter prompts (no examples to resend, so lower cost and latency), and often the ability to use a smaller, cheaper model.

4. LoRA: fine-tuning on a budget

A language model has hundreds of millions to billions of weights. Updating all of them needs a lot of GPU memory and produces a full new copy of the model. LoRA (low-rank adaptation) avoids that.

  • The original weight matrix W is frozen.
  • Next to it you add two small matrices, B and A. Their product is a correction with the same shape as W but only a small rank of freedom.
  • Take a 1024 x 1024 layer: W has 1,048,576 weights. With rank 8, B and A have 1024 x 8 + 8 x 1024 = 16,384 weights, about 1.6%.
  • You train only B and A. The saved adapter is a few megabytes. To use it, load the unchanged base model and plug the adapter in. You can keep many adapters (one per customer or task) for one base model.

The settings you will meet: rank r (capacity of the correction; 8 to 32 is typical), alpha (a scale for the correction, often twice r), dropout (a little regularization), and the target modules (which layers get adapters). The training loop itself is the same as in Module 3.

5. Preparing the training data

Each example is an input and the output you want, written in the chat format that the model was built for: a system message with the task, a user message with the input, an assistant message with the answer.

  • Mask the prompt. At run time the prompt is given, so there is nothing to learn from it. Setting its labels to -100 makes PyTorch skip it.
  • Add the end-of-text token after the answer. Otherwise the model learns the answer but never learns to stop.
  • Quality over quantity. Inconsistent or wrong answers teach inconsistency. A few hundred clean examples often beat thousands of messy ones.
  • Cover the variety of real inputs: typos, long and short, edge cases, and examples where the right answer is "none" or "other".
  • Split first. Train, validation and test must not share inputs (you saw why in Module 4). Never tune on the test set.

6. Comparing fairly

A fair comparison needs one test set, one scoring rule and one measuring function for every system. In the notebook each system is wrapped as a predict function that returns the text and the token counts, and one evaluate_system() measures them all.

  • Quality: the share of test examples answered correctly. The score ignores harmless differences such as spacing, key order, or chatter around a JSON object.
  • Format validity: how often the whole answer is exactly the required format. This is stricter, and it catches a model that is right but messy. Messy output breaks the program that reads it, so for a product it matters as much as accuracy.
  • Latency: the average seconds per request, measured around the call.
  • Tokens in and out: the basis of the cost.

Always include the untuned small model as a baseline. It shows how much the fine-tuning really added.

7. Cost and break-even

There are two ways to pay for a model:

  • A hosted API charges per token. Cost per 1,000 requests = 1,000 x (input tokens / 1,000,000 x input price + output tokens / 1,000,000 x output price).
  • A model you host costs the GPU time each request uses. Cost per 1,000 requests = 1,000 x seconds per request / 3,600 x GPU price per hour.

Prompting a large model has no up-front cost but a high price per request (especially with long few-shot prompts). Fine-tuning has the opposite shape: a one-time cost, then a low price per request.

saving per request  = (cost_per_1k_baseline - cost_per_1k_new) / 1000
break-even requests = one_time_cost / saving_per_request

Example: $5 once, $2.00 vs $0.50 per 1,000 requests
         saving = (2.00 - 0.50) / 1000 = $0.0015 per request
         break-even = 5 / 0.0015 = 3,333 requests
Count the hidden costs too. Someone has to label the data. The model has to be retrained when the task or the data changes. Someone has to host and monitor it. A fair business case includes these, and you should say so in your recommendation. Also, the prices in the notebook are placeholders: look up current prices before you show a table to anyone.

8. How much data do you need?

For a narrow task, 100 to 500 good examples is a common range. A useful rule: train on 25, 50, 100 and all of your examples, plot the curve, and stop collecting when it flattens. If the curve is still climbing steeply at your full dataset, more data will help. If it is flat, the limit is the model or the task definition, not the amount of data.

9. When not to fine-tune

  • Your information changes often. Use RAG and update the documents.
  • Prompting already meets the target. Do not add complexity for nothing.
  • You have little or poor data. A weak dataset gives a weak model.
  • The task keeps changing. Every change means new data and a new training run.
  • Volume is very low. The break-even point may never be reached.

And remember the opposite case too: with very high volume, strict privacy needs, or a need for fast answers, fine-tuning a small model can be the right call.

10. Key terms

TermPlain meaning
Fine-tuningTraining a pretrained model further on your examples
Few-shot promptingShowing worked examples inside the prompt, with no training
LoRAFine-tuning by training small added matrices and freezing the rest
Rank (r)The size of LoRA's small matrices, which sets their capacity
AdapterThe small file of trained LoRA weights, plugged into the base model
Label maskingSetting the labels of prompt tokens to -100 so that they are not learned
LatencyThe time one request takes
Break-evenThe volume at which a one-time cost has paid for itself

11. Common pitfalls

  • Fine-tuning before trying a good prompt with examples.
  • Training on the prompt as well as the answer.
  • Forgetting the end-of-text token, so the model never stops.
  • Testing on examples that were in the training data.
  • Comparing systems with different test sets or different scoring.
  • Ignoring the examples inside the few-shot prompt when counting the large model's cost.
  • Ignoring the one-time and ongoing costs of fine-tuning.

12. Check yourself

Try each question first, then open the answer.

Question 1: A weight matrix is 4096 x 4096. With LoRA rank 8, how many weights do you train for that matrix, and what fraction of the matrix is that?

B is 4096 x 8 and A is 8 x 4096, so 2 x 4096 x 8 = 65,536 weights. The matrix has 4096 x 4096 = 16,777,216 weights, so LoRA trains about 0.39% of it.

Question 2: Your fine-tuned model gets 95% on its training examples but 70% on the test set, while a few-shot prompted large model gets 85% on the test set. What do you conclude and what do you try?

The gap between 95% and 70% means the model is overfitting its training examples, and on the test set the prompted large model is currently better. Check for duplicated or inconsistent training data, add more varied examples, train for fewer epochs or with more dropout, and re-measure. Until the fine-tuned model wins on the test set, the honest recommendation is the prompted model.

Question 3: Fine-tuning costs $12 once and saves $0.80 per 1,000 requests. At 20,000 requests a day, how long until it breaks even?

The saving is $0.80 / 1,000 = $0.0008 per request. Break-even = 12 / 0.0008 = 15,000 requests. At 20,000 requests a day that takes 0.75 of a day, about 18 hours.
