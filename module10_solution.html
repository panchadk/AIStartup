Step 2: a privacy-safe log record

Every field is a fact about the request, not its content. The short hash lets you notice that the same input arrived twice, or compare the traffic of two weeks, without keeping what people typed.

def make_log_record(text, label, score, latency_ms):
    return {"ts": datetime.now(timezone.utc).isoformat(timespec="seconds"),
            "input_chars": len(text),
            "input_sha256": hashlib.sha256(text.encode("utf-8")).hexdigest()[:12],
            "label": label, "score": round(float(score), 4), "latency_ms": round(float(latency_ms), 2)}

Step 3: the API

Three details matter. Invalid input is rejected with a 4xx status before the model runs, so bad requests cost nothing and cannot crash it. Only the model call is timed, so the latency you report is the model's. And logging happens after a successful prediction, so rejected requests never reach the log.

class PredictRequest(BaseModel):
    text: str

def create_app(predict_fn, log_fn=None):
    app = FastAPI(title="Ticket urgency API")

    @app.get("/health")
    def health():
        return {"status": "ok"}

    @app.post("/predict")
    def predict_endpoint(req: PredictRequest):
        text = req.text.strip()
        if not text or len(text) > 2000:
            raise HTTPException(status_code=422, detail="text must be between 1 and 2000 characters")
        t0 = time.perf_counter()
        label, score = predict_fn(text)
        latency_ms = (time.perf_counter() - t0) * 1000
        if log_fn is not None:
            log_fn(make_log_record(text, label, score, latency_ms))
        return {"label": label, "score": float(score), "latency_ms": latency_ms}

    return app

Step 5: latency summary

np.percentile interpolates between measurements, which is the usual convention. A list of 95 fast requests and 5 slow ones has a small average and a large tail, which is exactly why you report percentiles.

def summarize_latencies(latencies_ms):
    a = np.asarray(latencies_ms, dtype=float)
    return {"n": int(len(a)), "avg": float(a.mean()), "p50": float(np.percentile(a, 50)), "p95": float(np.percentile(a, 95)),
            "p99": float(np.percentile(a, 99)), "max": float(a.max())}

Step 6: capacity and cost

Capacity is the inverse of latency, times the workers. The cost of one request is the busy-time cost divided by utilization, because you pay for the idle time too: at 10% busy, each request carries the cost of the 90% of the time the machine waited.

def requests_per_second_capacity(avg_latency_s, workers=1):
    return workers / avg_latency_s

def cost_per_request(avg_latency_s, instance_dollars_per_hour, utilization):
    return avg_latency_s / 3600 * instance_dollars_per_hour / utilization

def monthly_cost(requests_per_day, cost_per_request_dollars, fixed_monthly=0.0):
    return requests_per_day * 30 * cost_per_request_dollars + fixed_monthly

If your Space does not work

  1. It says "Building" for a long time. Wait a few minutes, then open the Logs tab: a missing or misspelled library in requirements.txt shows up there.
  2. A "runtime error" about a file. app.py, requirements.txt and model.joblib must all be at the top level of the Space, not inside a folder. Check the exact file names.
  3. A warning or error about the scikit-learn version. A model saved with one version should be loaded by the same version. The notebook pins it in requirements.txt (scikit-learn==...). If you edited the file, restore the pin.
  4. The page loads but the answer is wrong or empty. Try the same text in the notebook with predict. If the notebook works and the Space does not, the saved model file is probably an old version: upload model.joblib again.
  5. The Space is "sleeping". Free Spaces sleep when nobody visits. Open the address and wait for it to wake up. The first request after a sleep is slow, which is normal.
  6. Your friend sees "private" or an error. Open Settings and set the Space to Public.

A sample capstone one-pager

  • Problem: small online shops get hundreds of support tickets a day. The few that are truly urgent are buried among questions and thanks, and owners find them hours late.
  • User: the shop owner or support lead, who gets a ranked list inside the helpdesk they already use, through an API that is called whenever a ticket arrives.
  • Why deep learning: a keyword rule misses chat-style messages and wrongly flags polite thanks. I will measure a rules baseline first. A learned model reads the whole message and can be retrained as customers change how they write.
  • Data: anonymized, labeled tickets from three pilot shops, with a written labeling guide and a fixed test set stamped with a fingerprint.
  • Success metric: recall of urgent tickets of at least 90% with precision of at least 70% on the fixed test set, p95 latency under 300 ms, and compute under 20 dollars a month at 10,000 tickets a day.
  • Risks: missed urgent tickets (so the threshold favours recall), a gap between channels (so check slices), and private data in tickets (so log only hashes and lengths).

What makes it a good one-pager: a specific user, a baseline that you will beat, a metric with a number on a test set you control, and an honest list of risks.

Sample answers to the written questions

  • Model versus everything else: for a small model like this one, the model itself takes about a millisecond, and the round trip (network, JSON, web server) takes a few times that. So if you needed it faster, optimizing the model would gain almost nothing: look at the network, the number of calls, or batching instead. For a large model the picture reverses, and the model dominates.
  • Cost at low traffic: the cost is almost entirely the machine being on, not your requests. That is why utilization matters more than the model speed here, and why a serverless option (pay per use) can win at low volume.
  • When to add a machine: when the peak requests per second get close to the capacity (leave headroom, for example plan for 60 to 70% of capacity), or when the p95 latency starts to rise under load.
  • Caching: repeated inputs become near-instant, so p50 and p95 drop when traffic repeats. The risks: after you update the model, cached answers are stale (clear the cache on deploy), and cached text sits in memory (cache a hash, or limit the size and time).

Common mistakes and what they look like

  • Validating after calling the model: bad requests reach the model, waste compute, and can crash it. Reject first.
  • Latency reported in seconds, or timing more than the model: numbers that cannot be compared. Report milliseconds and say what you timed.
  • Judging speed by the average only: the tail hides. Always report p95.
  • Logging the raw text: a privacy problem waiting to happen. Log lengths and hashes.
  • Training inside the server: a service loads a saved model and never trains while serving.
  • Ignoring idle time in the cost: the cost per request looks tiny, but the machine is paid for all day.
  • Testing the Space only from your own browser: you may be logged in. Open it in a private window, and ask someone else.
  • Putting keys or private data in the repository: keep both out of Git.
