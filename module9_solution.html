Step 2: the data quality report

Strip each text before comparing, so that "a" and "a " count as duplicates. Duplicates matter because a copy in the test set that also sits in the training set inflates the score.

def data_quality_report(examples):
    labels = [e["label"] for e in examples]
    counts = dict(Counter(labels))
    texts = [e["text"].strip() for e in examples]
    seen, dups = set(), 0
    for t in texts:
        if t in seen:
            dups += 1
        seen.add(t)
    return {"n": len(examples), "label_counts": counts, "imbalance_ratio": max(counts.values()) / min(counts.values()),
            "n_duplicates": dups, "n_empty": sum(1 for t in texts if not t)}

Step 4: metrics from scratch

The four cells of the confusion matrix are the foundation. Everything else is arithmetic on them. Guard every division: a model that never predicts the positive class has no precision to speak of, and the answer is 0.0, not an error.

def accuracy(y_true, y_pred):
    return sum(t == p for t, p in zip(y_true, y_pred)) / len(y_true)

def majority_baseline(y_true):
    return max(Counter(y_true).values()) / len(y_true)

def confusion_counts(y_true, y_pred, positive):
    tp = sum(t == positive and p == positive for t, p in zip(y_true, y_pred))
    fp = sum(t != positive and p == positive for t, p in zip(y_true, y_pred))
    fn = sum(t == positive and p != positive for t, p in zip(y_true, y_pred))
    tn = sum(t != positive and p != positive for t, p in zip(y_true, y_pred))
    return tp, fp, fn, tn

def precision_recall_f1(tp, fp, fn):
    p = tp / (tp + fp) if tp + fp else 0.0
    r = tp / (tp + fn) if tp + fn else 0.0
    f1 = 2 * p * r / (p + r) if p + r else 0.0
    return p, r, f1

Step 5: slices and the harness

slice_metrics is the same arithmetic inside each group. run_eval only calls the pieces you already wrote, which is the point: a harness is glue code, written once and run every time. Putting the test set fingerprint in the report lets anyone check that two reports are comparable.

def slice_metrics(examples, y_pred, key, positive):
    groups = {}
    for e, p in zip(examples, y_pred):
        groups.setdefault(e[key], []).append((e["label"], p))
    out = {}
    for g, pairs in groups.items():
        t, p = [a for a, _ in pairs], [b for _, b in pairs]
        tp, fp, fn, tn = confusion_counts(t, p, positive)
        pr, re_, _ = precision_recall_f1(tp, fp, fn)
        out[g] = {"n": len(pairs), "precision": pr, "recall": re_}
    return out

def run_eval(predict_fn, test_set, positive, slice_key=None):
    preds = [predict_fn(e["text"]) for e in test_set]
    y = [e["label"] for e in test_set]
    tp, fp, fn, tn = confusion_counts(y, preds, positive)
    p, r, f1 = precision_recall_f1(tp, fp, fn)
    return {"n": len(y), "accuracy": accuracy(y, preds), "majority_baseline": majority_baseline(y),
            "tp": tp, "fp": fp, "fn": fn, "tn": tn, "precision": p, "recall": r, "f1": f1,
            "slices": slice_metrics(test_set, preds, slice_key, positive) if slice_key else {},
            "failures": [{"text": e["text"], "label": e["label"], "pred": pr} for e, pr in zip(test_set, preds) if e["label"] != pr],
            "test_fingerprint": fingerprint(test_set)}

Step 7: failure analysis

Each failure goes into exactly one category, so that the counts add up and you can see the biggest one. Putting the specific rules first and "other" last means that a failure is explained by the most specific pattern that matches it.

def failure_breakdown(failures, rules):
    counts = Counter()
    for f in failures:
        tag = "other"
        for name, rule in rules.items():
            if rule(f["text"]):
                tag = name
                break
        counts[tag] += 1
    return sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))

Stretch: Cohen's kappa

Raw agreement flatters: if 95% of items are normal, two labelers who always say normal agree 95% of the time. Kappa subtracts the agreement you would expect by luck.

def cohens_kappa(a, b):
    n = len(a)
    po = sum(x == y for x, y in zip(a, b)) / n
    pe = sum((a.count(l) / n) * (b.count(l) / n) for l in set(a) | set(b))
    return 1.0 if pe == 1 else (po - pe) / (1 - pe)

A sample labeling guide (demo task)

urgent: the customer cannot work, or is losing money or data, or security is at risk, right now.
   Examples: "our whole site is down", "someone hacked my account".
normal: everything else: questions, thanks, suggestions, problems that can wait.
   Examples: "how do I change my billing address", "thanks for the quick reply".
Edge cases and rules:
 - A message that says "urgent" but is only thanks or a joke is NORMAL: judge the situation, not the word.
 - "This is not urgent" is NORMAL, even if it mentions login or payment.
 - A problem affecting one user or happening sometimes is urgent only if work is blocked.
 - When two labelers disagree, the lead decides and the guide gets the new rule.

Sample answers to the written questions

  • Imbalance and accuracy: in the demo about 12% of the tickets are urgent, so a model that always says normal is about 88% accurate. That is the bar to beat, and a model that is 95% accurate with a recall of 61% is much less impressive than it looks: it misses four of every ten urgent tickets.
  • Precision versus recall: care about recall when a miss is expensive (an urgent ticket left unanswered, a fraud case missed, a defective part shipped). Care about precision when a false alarm is expensive (a legitimate customer blocked, a person interrupted, a costly manual review).
  • Slices: in the demo the recall for chat messages is far lower than for email. Plausible causes: chat messages are short and lowercase, they are fewer in the training data, and a bag of words has less to work with in a short message. Remedies: more chat examples, features that suit short text, or a separate threshold per channel. For your own task also check language, region, length, device and customer type, and always ask who is hurt when the model fails.
  • Conclusion on the fix: class weights raise recall by making a missed rare example cost more. The price is usually lower precision (more false alarms). Whether that is worth it depends on the relative cost of the two mistakes, which is a business decision and not a modelling one. Say what you measured, on the same test set, and what you would do next.
  • Disagreements between labelers: they cluster on borderline items (a problem that happens sometimes, a mild error). The fix is a written rule in the guide for exactly those cases, then relabeling the items that the rule touches.

Common mistakes and what they look like

  • Reporting accuracy only: a high number that hides a model that finds nothing. Always put the majority baseline beside it.
  • Tuning on the test set: the final score is no longer honest. Use the validation set for analysis and the test set once, at the end.
  • Duplicates across splits: inflated scores. Clean first, then split.
  • Dividing by zero in precision or recall: a crash on the model that predicts no positives. Return 0.0.
  • Changing the test set between reports: the comparison is unfair. The fingerprint catches it.
  • Looking only at the average: a group can be failed completely while the overall number looks fine.
  • Vague failure categories ("model got it wrong"): they give no direction. Categories should name a pattern in the input.
  • Fixing the small category first: effort with little effect. Sort by count.
  • A labeling guide with no edge cases: labelers invent their own rules, and agreement drops.
