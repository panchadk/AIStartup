1. Bugs that do not crash

In normal programming, a bug usually gives an error message. In machine learning, the worst bugs give no error at all. The code runs, numbers print, and the model produces output. It is just quietly wrong: a bit worse than it should be, or secretly cheating, or fine on your data and useless in the real world.

That makes debugging a different skill. You cannot wait for a crash. You must look: print things, plot things, compare things. This module trains that habit with five realistic bugs.

2. Debug in order

When a model misbehaves, the cause is almost always in one of four places. Check them in this order, cheapest first, and stop at the first thing that looks wrong:

Why this order? Data and loss bugs are the most common and the cheapest to check. Changing the model is expensive and rarely the answer. A beginner's instinct is to add layers or train longer. An experienced engineer first prints a batch.

The golden rule: do not tune a model that you have not shown can learn. Tuning a broken pipeline is wasted time, and it can even hide the bug.

3. Two powerful tricks

Trick 1: overfit one batch

Take a single small batch and train on it over and over. A correct model and training loop will drive the loss on that batch to nearly zero, because memorizing 64 examples is easy. If the loss will not go down, something basic is broken: the loss, the labels, the optimizer, or the learning rate.

Trick 2: beat a baseline, and know your starting loss

  • Baseline: a trivial predictor, such as always guessing the most common class. If your model barely beats it, either the problem is hard or something is wrong.
  • Expected first loss: a model that guesses randomly among K classes has a cross-entropy loss near ln(K). For 3 classes that is 1.1, and for 10 classes it is 2.3. If your first loss is 50 or nan, the setup is broken before training even starts.

5. Data leakage

Data leakage means information from the test data sneaks into training, so the test score looks better than reality. The model is graded on questions it has effectively seen.

Common forms of leakage:

  • Duplicates and near-duplicates across the split, such as augmented copies, repeated rows, or frames from the same video. Split by group.
  • Preprocessing fitted on all the data, such as a scaler using the mean and standard deviation of train plus test. Fit it on the training data only, then apply it to the rest. The effect is often small, but it is a bad habit and sometimes a big problem.
  • The future leaking into the past, in time-ordered data: always split by time, with the test set after the training set.
  • A feature that is secretly the answer, such as an ID that encodes the label.
The test: a leaky test set gives a score that is too good to be true. If your model does far worse on genuinely new data than on the test set, suspect leakage first.

6. Training mode and evaluation mode

Some layers behave differently while training and while predicting. PyTorch lets you switch with model.train() and model.eval().

  • In training mode, Dropout randomly drops units, so repeating the same evaluation gives different numbers. BatchNorm uses the statistics of the current batch.
  • In evaluation mode, Dropout is off and BatchNorm uses the running statistics it collected during training. Results are deterministic.
  • torch.no_grad() is a separate switch: it stops PyTorch from tracking gradients, which saves time and memory when you are only predicting.

The sanity test is simple: evaluate the same model on the same data twice. If the numbers differ, the model is not in evaluation mode.

7. Order, shuffling and the loss

Shuffling

Gradient descent assumes each batch is a fair sample of all the data. If batches arrive sorted, the model repeatedly learns class A, then forgets it while learning B, then forgets both while learning C. Always shuffle the training data. Be extra careful with files that are exported sorted.

The loss and what it expects

  • nn.CrossEntropyLoss wants raw scores (logits) and integer class labels. It applies the softmax itself. A model that also applies softmax gets squashed outputs and a loss that can never go low.
  • Always look at the loss as well as the accuracy. Accuracy only cares which output is largest, so it can look healthy while the loss tells you something is wrong.

The learning rate

A learning rate range test trains briefly at several learning rates and looks at how fast the loss falls. Pick a value in the region where it falls quickly without blowing up. A rate that is far too high gives enormous losses, and one that is far too low barely moves the loss.

9. Common pitfalls

  • Changing the model before checking the data and the loss.
  • Trusting accuracy and ignoring the loss.
  • Believing a score that is too good to be true.
  • Tuning a pipeline that cannot yet overfit one batch.
  • Changing three things at once, so you cannot tell which one fixed the bug.
  • Not writing down what the bug was, so you hit it again next month. That is what your checklist is for.

10. Check yourself

Try each question first, then open the answer.

Question 1: Your 3-class model's first loss is 4.7 instead of about 1.1. Name two things you would check.

Check the scale of the inputs (huge unnormalized values make huge outputs), the learning rate and initialization, and that the labels are valid integers in the right range. A first loss far above ln(3) means the setup is off before training starts.

Question 2: You standardized the data with the mean and standard deviation of the whole dataset, then split it. Is that a problem?

Yes, it is a (usually small) leak: the test rows influenced the preprocessing. Compute the statistics on the training rows only and apply them to the validation and test rows. It is a good habit even when the effect is small.

Question 3: The same model on the same data gives accuracy 0.91, then 0.89. What do you suspect?

The model is still in training mode, so dropout is randomly switching units off. Call model.eval() before evaluating, and torch.no_grad() around it.
