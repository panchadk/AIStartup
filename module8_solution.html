Step 2: scoring answers

A forgiving score looks for a JSON object inside the answer and re-writes it in a canonical form, so spacing, key order, and chatter or code fences around it do not count as errors. Format strictness is measured separately by format_valid, so you can see a model that is right but messy.

def normalize_output(text):
    m = re.search(r"\{.*\}", text, re.S)
    if m:
        try:
            return json.dumps(json.loads(m.group(0)), sort_keys=True)
        except Exception:
            pass
    return " ".join(text.lower().split())

def is_correct(pred, gold):
    return normalize_output(pred) == normalize_output(gold)

Step 3: evaluate_system

Time only the call to the model, collect the token counts it reports, and average everything at the end. Because every system (small, large, fine-tuned) is wrapped as the same kind of predict function, one evaluator measures all of them fairly.

def evaluate_system(predict_fn, examples):
    correct = valid = 0
    lat, n_in, n_out = [], [], []
    for ex in examples:
        t0 = time.perf_counter()
        r = predict_fn(ex["input"])
        lat.append(time.perf_counter() - t0)
        correct += is_correct(r["text"], ex["output"])
        valid += format_valid(r["text"])
        n_in.append(r["input_tokens"]); n_out.append(r["output_tokens"])
    n = len(examples)
    return {"quality": correct / n, "valid_rate": valid / n, "latency_s": sum(lat) / n,
            "avg_in": sum(n_in) / n, "avg_out": sum(n_out) / n, "n": n}

Step 5: the few-shot prompt

Worked examples first, then the new message, ending on an open Answer: so that the model continues the pattern. Note the cost: every request carries all the examples again.

def build_fewshot_prompt(shots, input_text):
    system = TASK_SYSTEM
    blocks = [f"Message: {s['input']}\nAnswer: {s['output']}" for s in shots]
    user = "Examples:\n\n" + "\n\n".join(blocks) + f"\n\nMessage: {input_text}\nAnswer:"
    return system, user

Step 6: training data with the prompt masked

The prompt and the answer are tokenized separately and joined, so the boundary between them is exactly the boundary the model will see at run time. The labels are -100 for every prompt position, so the loss (and therefore the learning) comes only from the answer and the end-of-text token. Without the end-of-text token the model would never learn to stop.

def to_chat(example):
    return [{"role": "system", "content": TASK_SYSTEM},
            {"role": "user", "content": example["input"]},
            {"role": "assistant", "content": example["output"]}]

def tokenize_example(example, tokenizer, max_len=256):
    messages = to_chat(example)
    prompt_text = tokenizer.apply_chat_template(messages[:-1], tokenize=False, add_generation_prompt=True)
    prompt_ids = tokenizer(prompt_text, add_special_tokens=False)["input_ids"]
    completion_ids = tokenizer(example["output"] + tokenizer.eos_token, add_special_tokens=False)["input_ids"]
    return {"input_ids": (prompt_ids + completion_ids)[:max_len],
            "labels": ([-100] * len(prompt_ids) + completion_ids)[:max_len]}

Step 9: costs and break-even

An API charges per token, so cost is tokens times price, per million. A model you host costs the GPU time that each request occupies. Break-even asks how many requests it takes for the saving per request to repay a one-time cost.

def api_cost_per_1k(avg_in, avg_out, price_in_per_m, price_out_per_m):
    return 1000 * (avg_in / 1_000_000 * price_in_per_m + avg_out / 1_000_000 * price_out_per_m)

def gpu_cost_per_1k(latency_s, gpu_dollars_per_hour):
    return 1000 * latency_s / 3600 * gpu_dollars_per_hour

def break_even_requests(one_time_cost, cost_per_1k_baseline, cost_per_1k_new):
    saving_per_request = (cost_per_1k_baseline - cost_per_1k_new) / 1000
    if saving_per_request <= 0:
        return float("inf")
    return one_time_cost / saving_per_request

A sample recommendation

There is no single right answer. A good recommendation names an option, cites numbers for all three axes, and says what would change it. For example:

I recommend the fine-tuned small model. On the test set it reached 93% quality against 94% for the prompted large model, and it answered in the exact JSON format 100% of the time (the large model added chatter around the JSON in 17% of answers). It answers in 0.3 seconds against 1.2, and it costs $0.03 per 1,000 requests against $0.60, because it needs no examples in the prompt. Training cost about $0.02 once, which pays for itself after about 40 requests. This would change if volume were very low (prompting needs no setup), if the task or labels changed every week (retraining is a chore), or if I needed the large model's stronger judgment on rare hard cases.

These numbers are an illustration. Your numbers will differ, and your recommendation must follow your table. If your fine-tuned model was worse, say so, and say what it would take (more data, more epochs, a bigger base model) to change the answer.

If the fine-tuned model is not better

  1. Check the labels. Print one tokenized example and confirm that only the answer positions are not -100.
  2. Check the loss. It should fall steadily. If it stays high, raise the learning rate a little or train for more epochs.
  3. Check the data. Wrong, inconsistent or duplicated answers teach the model to be inconsistent. Fix the data before the settings.
  4. Raise the rank (for example 16 to 32) or adapt more layers, if the task needs more capacity.
  5. Use a larger base model if the small one lacks the skill (for example, it cannot read numbers reliably).
  6. Check the test. A model that got the content right but the format slightly wrong scores badly. Look at a few wrong answers before changing anything.

Common mistakes and what they look like

  • Computing the loss on the prompt too: training is slower and the model learns to echo the prompt. The tokenization self-check shows the masked positions.
  • Leaving out the end-of-text token: the model produces a correct answer and then keeps writing. Quality drops and latency rises.
  • Testing on training data: a perfect score that means nothing. The dataset check requires disjoint train and test sets.
  • Comparing systems on different test sets or with different scoring: the table is meaningless. Wrap every system as a predict function and use one evaluator.
  • Counting the cost of the model but not of the examples in the prompt: the few-shot prompt is sent again with every request, so it often dominates the cost of the large model.
  • Ignoring the one-time cost and the upkeep: fine-tuning must be redone when the task or data changes.
  • Using placeholder prices as real ones: look up the current prices before showing the table to anyone.
  • Putting private data or an API key in the repository: keep both out of Git.
