Step 2: does the plan fit?

Only the must-have tasks have to fit, shared among the team, and the buffer is not optional: plans always run late. Exactly enough time still fits.

def schedule_check(plan, team_size, days_available, buffer=0.2):
    total = sum(t["days"] for t in plan)
    must = sum(t["days"] for t in plan if t["must"])
    per_person = must / team_size
    needed = per_person * (1 + buffer)
    return {"total_days": total, "must_days": must, "per_person_days": per_person,
            "needed_with_buffer": needed, "fits": needed <= days_available, "spare_days": days_available - needed}

Step 3: do the interfaces fit?

Each pair of neighbours must agree on the type that passes between them, and every component must have all four fields, including one owner. The check costs nothing, and the mismatch it finds would otherwise cost a team a night before demo day.

def check_pipeline(components):
    problems = []
    for i, c in enumerate(components):
        for key in ("name", "input", "output", "owner"):
            if not c.get(key):
                problems.append(f"Component {c.get('name', '#' + str(i + 1))} is missing {key!r}.")
    for a, b in zip(components, components[1:]):
        if a.get("output") and b.get("input") and a["output"] != b["input"]:
            problems.append(f"{a['name']} outputs {a['output']!r} but {b['name']} expects {b['input']!r}.")
    return problems

Step 5: the evaluation harness

The harness is generic: a prediction function, an evaluation set, and a function that scores one example from 0 to 1. A partial score (for example, the fraction of fields that are right) counts as a failure if it is below 1.0, so that the failures list shows everything that needs work. The fingerprint proves that the model and the baseline were measured on the same set.

def metric_fn(pred, example):
    return 1.0 if pred == example["expected"] else 0.0

def run_capstone_eval(predict_fn, eval_set, metric_fn):
    scores, failures = [], []
    for e in eval_set:
        pred = predict_fn(e["input"])
        s = float(metric_fn(pred, e))
        scores.append(s)
        if s < 1.0:
            failures.append({"input": e["input"], "expected": e["expected"], "pred": pred, "score": s})
    return {"n": len(eval_set), "score": sum(scores) / len(scores), "failures": failures, "fingerprint": fingerprint_eval(eval_set)}

Stretch: summarizing user tests

Counting issues across users shows which problem is most common, which is what to fix first. Completion rate matters more than satisfaction: someone who could not finish the task is not helped by being polite.

def summarize_user_tests(tests):
    counts = Counter(issue for t in tests for issue in t["issues"])
    return {"n": len(tests), "completion_rate": sum(t["completed"] for t in tests) / len(tests),
            "avg_satisfaction": sum(t["satisfaction"] for t in tests) / len(tests),
            "top_issues": sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))}

A sample project card (the demo project)

  • Problem: small online shops get hundreds of tickets a day, and the urgent ones are found hours late.
  • User: the shop owner or support lead, through their existing helpdesk.
  • Why deep learning: keyword rules miss chat-style messages and flag polite thanks that contain the word urgent; baseline measured first.
  • Data: labeled tickets with a written guide, split with a fixed, fingerprinted evaluation set.
  • Metric and target: accuracy on a balanced evaluation set, target 0.90, against a naive keyword baseline.
  • Scope: must have a classifier, a pipeline, an evaluation against a baseline and a labeling guide; nice to have a try-it page and a per-channel breakdown; out of scope auto-replies and other languages.

Notice how short the must-have list is, and how the out-of-scope list protects it.

If your model does not beat the baseline

That is a result, not a failure of the project. In order:

  1. Is the baseline too good? If a simple rule scores nearly as high, your problem may not need deep learning. Say so honestly, and think about where the learned model would add value (harder cases, changing language, scale).
  2. Is the evaluation set fair? A tiny or unrepresentative set gives noisy numbers. Check its size and where it came from.
  3. Is the data the problem? Inconsistent labels or too few examples of the hard cases cap any model. Read the failures.
  4. Is the model the problem? Only now try a different or larger model, or fine-tuning.
  5. Is the target realistic? A target chosen before you saw any data may be wrong. Change it, but write down why.

Sample interpretation

The model scores 0.98 on the balanced evaluation set against 0.46 for the naive keyword rule, and reaches the target of 0.90. The gap is large because the keyword rule misses most real urgent tickets, which seldom contain the word urgent. The evaluation set is balanced and the data is templated, so real accuracy will be lower, and the next step is to measure on a small sample of real tickets.

Common mistakes and what they look like

  • Everything is a must-have: the plan never fits, and the project is half-finished on demo day. Cut until it fits, with the buffer.
  • Building layer by layer: the model is perfect, but nothing connects to anything until the last week. Build the thin slice first.
  • Interfaces agreed in people's heads: the parts do not fit when joined. Write them down, with one owner each.
  • Inventing "real" inputs that are easy: the smoke test passes and the first real user crashes it. Use inputs as users really send them.
  • Evaluating on data the model trained on: a lovely number that means nothing. Keep a fixed, unseen set.
  • No baseline: you cannot say if 85% is good. Always compare.
  • Tuning the target to fit the result: the target must be set from what the user needs.
  • Waiting until the end to show anyone: real users find the important problems in the first hour.
