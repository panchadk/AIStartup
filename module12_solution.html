Step 1: hardening

Validation comes first so that bad input never reaches the model. The wrapper contains every kind of failure (it catches Exception, not one specific type), tells the user something generic, and sends the real details to the log. Never put the exception text in the answer: it can reveal file paths, library names or secrets.

def validate_input(raw, max_chars=2000):
    if not isinstance(raw, str):
        return False, "input must be text"
    text = raw.strip()
    if not text:
        return False, "input is empty"
    if len(text) > max_chars:
        return False, f"input is too long (more than {max_chars} characters)"
    return True, ""

def safe_predict(predict_fn, raw, log_fn=None, max_chars=2000):
    ok, reason = validate_input(raw, max_chars)
    if not ok:
        return {"ok": False, "error": reason}
    t0 = time.perf_counter()
    try:
        result = predict_fn(raw.strip())
    except Exception as e:
        if log_fn is not None:
            log_fn(f"{type(e).__name__}: {e}")
        return {"ok": False, "error": "the model could not process this input"}
    return {"ok": True, "result": result, "latency_ms": (time.perf_counter() - t0) * 1000}

Step 2: unit economics

Gross margin is measured against revenue, not against cost. Break-even asks how many requests it takes for the profit per request to repay the fixed costs, and if you lose money on every request, the answer is never. The price for a target margin comes from solving margin = (price - cost) / price.

def unit_economics(price_per_request, cost_per_request, fixed_monthly, requests_per_month):
    revenue = price_per_request * requests_per_month
    variable = cost_per_request * requests_per_month
    gross = revenue - variable
    return {"revenue": revenue, "variable_cost": variable, "gross_profit": gross,
            "gross_margin": gross / revenue if revenue else 0.0, "net_profit": gross - fixed_monthly,
            "break_even_requests": fixed_monthly / (price_per_request - cost_per_request) if price_per_request > cost_per_request else float("inf")}

def price_for_margin(cost_per_request, target_gross_margin):
    return cost_per_request / (1 - target_gross_margin)

Step 4: the pitch timing

Order matters as much as length: the same sections in another order are a different pitch. The longest section should be the demo.

REQUIRED_ORDER = ["problem", "demo", "how_it_works", "results", "cost_and_market", "next_steps"]

def check_pitch_timing(slides, limit_seconds=300):
    names = [s["section"] for s in slides]
    total = sum(s["seconds"] for s in slides)
    return {"total_seconds": total, "within_limit": total <= limit_seconds, "order_ok": names == REQUIRED_ORDER,
            "missing": [s for s in REQUIRED_ORDER if s not in names], "longest": max(slides, key=lambda s: s["seconds"])["section"]}

What a strong technical report and README look like

  • Summary: the headline in two sentences, with a number against a baseline.
  • Data: source, size, labeling guide, how the test set is kept fixed.
  • Model choice: what you chose, why, and what you compared it with.
  • Evaluation: numbers, not adjectives: your metric, the baseline's, the target, latency, cost.
  • Limitations: at least three specific points covering failure cases, data gaps and risks. "It may make mistakes" is not a limitation. "Short chat messages are missed more than half the time" is.
  • README: what it does, a link to the demo, numbered steps to run it, results, limitations.

Questions to expect on demo day, and honest answers

  • What is your baseline, and how much better are you? State both numbers and the gap.
  • What does it get wrong? Name your biggest failure pattern, with an example.
  • What does it cost to run, and who pays? Cost per request, price, margin, and what the customer pays today.
  • What stops someone copying it? Your data, your integration, your speed of learning, not the model.
  • What would you do with the next month? Your top two next steps from the failure analysis.

Sample answers to the written questions

  • Which scenario loses money, and why? The pessimistic one: low volume and a lower price cannot cover the fixed costs. The compute is almost free, so the fixed costs and the volume decide it. What you must believe for the base case: customers will pay roughly a cent per ticket, and enough shops will send enough tickets.
  • The number an investor questions first: usually the price (no customer has confirmed they will pay it) or the volume. Both are assumptions, so be honest that they are, and say how you would test them (pilot customers).
  • The stranger test: the first thing that confuses a stranger is almost never the model. It is a missing instruction, an unclear page, or a slow first load. Fix that before the demo.

Common mistakes and what they look like

  • Leaking the exception text to the user: a message such as "KeyError: api_key" tells an attacker where to push. Generic message out, details to the log.
  • Catching only one kind of error: the first different failure takes the service down. Catch Exception.
  • Pricing from cost alone: compute costs a fraction of a cent, so cost-plus pricing gives you a business that cannot cover a single month of fixed costs. Price from the value to the customer.
  • Believing the optimistic scenario only: the pessimistic scenario is the one that tells you whether you survive.
  • Generic limitations: they signal that you did not look. Be specific, with numbers.
  • A pitch that starts with the model: the audience does not yet know why they should care. Start with the problem, then show it working.
  • An unrehearsed live demo: it fails on the one input you did not test. Rehearse with a timer, and keep a backup recording.
  • A Space that is asleep or private: the demo fails in front of the audience. Open it a minute before, and check from a private window.
  • Calling it deployed without a stranger trying it.
