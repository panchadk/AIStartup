1. The big picture

So far every model lived in a notebook: you ran a cell and saw an answer. A product is different. Strangers use it, at any hour, from their own devices, and they expect it to be quick. The step between those two worlds is deployment.

It also changes what you care about. In a notebook you ask is the model accurate? In production you also ask is it fast, is it cheap, is it up, and is it safe with people's data? This module teaches you to answer all four with numbers.

2. APIs: how programs talk to your model

An API is an agreement about how one program asks another for something. Over the web, the usual agreement is HTTP: the client sends a request to an address, and the server sends back a response with a status code.

  • JSON is the common text format for the data: {"text": "..."} in, {"label": "urgent", "score": 0.95} out.
  • GET asks for something (like /health). POST sends data to be processed (like /predict).
  • Status codes: 2xx means success, 4xx means the client made a mistake (for example 422 for invalid input), 5xx means the server failed. Using the right code lets callers react correctly.

3. Building one with FastAPI

FastAPI is a Python library that turns functions into endpoints. You write the function; it handles the web part. A few ideas matter:

  • Validate input at the door. The request body is described by a small class (PredictRequest), and FastAPI rejects a missing field automatically. You add the rest: reject empty or oversized text before the model runs. This protects the model and your bill.
  • A health endpoint. GET /health returns "ok" if the service is alive. Hosting platforms call it to decide whether to restart you.
  • Load once, serve many. The model is loaded when the server starts, not at every request. Loading is slow; predicting is fast.
  • Automatic documentation. FastAPI builds a documentation page at /docs from your code. Other developers can try your API from it.
  • Test without a server. A test client calls the app directly, so you can check good and bad requests in a second. You did exactly that in the self-check.
Never train inside the server. A service loads a saved model file and only predicts. If the model needs to change, you train elsewhere, save a new file, and redeploy.

4. Putting it online

An API is for programs. People need a web page. Gradio turns a Python function into one in a few lines (a text box in, a label out), and Hugging Face Spaces hosts it for free and gives it a public address.

  • A Space needs three files: app.py (the page), requirements.txt (the libraries), and your model.joblib.
  • Pin library versions. A model saved with one scikit-learn version should be loaded with the same one. The notebook writes the pin for you.
  • Free Spaces sleep when unused. The first visit after a sleep is slow.
  • Test as a stranger: open the address in a private window, and ask someone else to try it. "Works on my machine" is not deployed.

5. Latency

Latency is how long one request takes. Users feel it directly: under about 100 ms feels instant, around a second is noticeable, and several seconds loses people.

  • The average mixes everything together and understates the slow requests.
  • The median (p50): half of the requests are faster than this.
  • The 95th percentile (p95): 95 of every 100 requests finish within this time. One in 20 is slower. Products usually set their goals in p95 or p99.
  • Measure what the user feels (the whole round trip, from the client) and what the model contributes (timed inside the server). The gap is the network, the data conversion and the web server, which you may be able to reduce in a different way from the model.

Ways to make it faster: a smaller or faster model; caching repeated inputs; batching several inputs into one call to the model; shorter inputs; running close to your users; keeping the model loaded (avoiding a slow cold start).

6. Cost

A server costs money whether or not anyone calls it: you rent the machine by the hour. So the cost of one request depends on three things:

capacity            = workers / seconds_per_request          (requests per second)
cost per request    = seconds_per_request / 3600 x dollars_per_hour / utilization
monthly cost        = requests_per_day x 30 x cost_per_request + fixed costs
  • Utilization is the share of the time that the machine is busy. At 5% busy, each request carries the cost of the 95% idle time, so it is 18 times as expensive as at 90% busy.
  • That is why low-traffic services are expensive per request, and why pay-per-use options can beat a rented machine until your traffic grows.
  • Capacity planning: if the peak is 150 requests per second and one worker handles 40, you need at least 4 workers, and in practice more, because you want headroom (plan for 60 to 70% of capacity at the peak).

The prices in the notebook are placeholders. Look up real prices before you show a number to anyone.

7. Logging and monitoring

Once your service is live you cannot watch it. Logs are how you see what it is doing: how many requests, how fast, what labels, how many were rejected. They let you debug failures and notice changes (a rise in latency, more errors, a shift in the labels that may mean that the world changed).

User text is often private: names, passwords, health details. Keeping it creates a risk (a leak) and an obligation (privacy rules). So log facts: a timestamp, the length, a short hash (to spot repeated inputs), the result and the latency. If you really must keep inputs to improve the model, do it deliberately, with consent, secure storage and a deletion plan.

8. Your capstone idea

In Modules 11 and 12 you build and ship your own prototype. A good idea fits on one page and answers six questions:

  1. Problem: whose problem, and how painful is it today?
  2. User: who exactly, and how will they use it?
  3. Why deep learning: what simpler approach (rules, search, a spreadsheet) would you try first, and why might it fall short? If a simple method works, use it.
  4. Data: where does it come from, who labels it, and how will you keep a fixed test set?
  5. Success metric: a number on your test set that means "good enough", plus a speed or cost limit if it matters.
  6. Risks: wrong answers, unequal performance, privacy, cost.

Pick something you can finish in a few weeks, with data you can actually get. A small idea that works beats a big one that does not.

9. Key terms

UtilizationThe share of time a machine is busy
Cold startA slow first request after a service has been idle
CachingRemembering answers so that repeated inputs are not recomputed

10. Common pitfalls

  • Checking input after calling the model, instead of before.
  • Reporting only the average latency.
  • Counting only the busy time in the cost and forgetting the idle time.
  • Logging the private content of requests.
  • Loading or training the model at every request.
  • Not pinning library versions, so the model will not load in production.
  • Declaring it "deployed" without testing it as a stranger would.

11. Check yourself

Try each question first, then open the answer.

Question 1: Over 1,000 requests, the p50 is 40 ms and the p95 is 400 ms. What does this mean for users, and what would you do?

Half of the requests take 40 ms or less, but 1 request in 20 (50 of the 1,000) takes 400 ms or more, ten times slower. The average would look fine and hide this. Look at what the slow requests have in common: unusually long inputs, a cold start after idle time, heavy load at that moment, or a slow dependency. Fix the cause of the tail rather than the typical case.

Question 2: A model takes 50 ms per request on a machine that costs 0.20 dollars per hour and is busy 25% of the time. What is the cost per request, and per 1,000 requests?

Busy-time cost: 0.05 / 3600 x 0.20 = 0.0000027778 dollars. Divide by the utilization 0.25: 0.0000111 dollars per request. Per 1,000 requests that is about 0.0111 dollars (1.1 cents).

Question 3: Peak traffic is 150 requests per second and one worker handles 40 per second. How many workers do you need?

150 / 40 = 3.75, so at least 4 workers just to keep up at the peak. That leaves no headroom, so a realistic plan aims for 60 to 70% of capacity at the peak: 150 / (40 x 0.7) = 5.4, so about 6 workers.
