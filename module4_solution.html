Module 4: Reference solution

Try it yourself first. Open this page only after your own honest attempt. Finding the bug is the whole point of the module, and reading the answer first removes the learning. If you are stuck on one case, read only that case's "how to find it" steps.

The five bugs below all share one trait: the code runs without an error. That is why you find them by looking (printing, plotting, comparing), not by waiting for a crash.

Case 1: leakage

What you see: Test accuracy about 0.91, but fresh data gives about 0.75. A gap that large means the test set is not behaving like new data.

How to find it:

  1. Compare the test score with a score on genuinely new data. They should be close. Here they are not.
  2. Ask what is special about this data: it contains 5 copies of every original sample. A random split of rows puts copies of the same sample on both sides.
  3. Check directly: set(groups[train_idx]) & set(groups[test_idx]) is large (about 400 shared samples), so the model is partly being tested on rows it memorized.

The fix:

# split by ORIGINAL sample (group), so no sample has copies on both sides
g = np.random.permutation(600)
train_idx = np.where(np.isin(groups, g[:480]))[0]
test_idx = np.where(np.isin(groups, g[480:]))[0]

# standardize using the TRAINING rows only
mean, std = X_raw[train_idx].mean(axis=0), X_raw[train_idx].std(axis=0)
X = (X_raw - mean) / std

Root cause (one line): Copies of the same sample ended up in both train and test, because I split rows instead of original samples. (A second, smaller leak: the scaler statistics used the test rows.)

The lesson: Whenever data has groups (patients, customers, augmented copies, frames of one video), split by group, never by row. After fixing it, the test score drops to an honest 0.69, and now matches the fresh score of about 0.74.

Case 2: stuck loss

What you see: Validation accuracy about 0.89 looks fine, but the training loss stalls at about 0.61 instead of falling toward 0.15.

How to find it:

  1. Look at the loss values, not just the accuracy. Accuracy only needs the largest output to be right.
  2. Print one row of model(x). The three outputs add up to 1: they are already probabilities.
  3. nn.CrossEntropyLoss applies a softmax itself, so the model's softmax is applied twice. The second softmax squashes the outputs, so even a perfect prediction gives a loss of about 0.55, which is the floor you see.

The fix:

# before:  nn.Linear(64, 3), nn.Softmax(dim=1))
model = nn.Sequential(nn.Linear(10, 64), nn.ReLU(), nn.Linear(64, 3))

Root cause (one line): The model applied softmax and CrossEntropyLoss applies it again, so the loss could not go below about 0.6.

The lesson: For classification, the model should output raw scores (logits). Apply softmax only when you want probabilities for display, never before CrossEntropyLoss. This bug is easy to miss because accuracy still looks fine.

Case 3: huge loss

What you see: The loss starts at about 464 and ends near 20, and validation accuracy is about 0.34, barely above random guessing for 3 classes.

How to find it:

  1. A 3-class model that guesses has a loss near 1.1. A loss of several hundred means the weights are being thrown far away on every step.
  2. The setting that controls the size of each step is the learning rate. Here it is 5.0, far too large for Adam.
  3. Run lr_range_test([1e-4, 1e-3, 1e-2, 1e-1]). The losses fall nicely for 1e-3 and 1e-2, and blow up at 1.0 and above.

The fix:

LR = 3e-3      # chosen with lr_range_test

Root cause (one line): The learning rate of 5.0 made every step huge, so the loss blew up instead of falling.

The lesson: Try a range of learning rates for a few epochs each and pick one in the region where the loss falls fastest without becoming unstable. For Adam, values between 1e-4 and 1e-2 are a common starting range.

Case 4: sorted data

What you see: Validation accuracy is only about 0.65, although a good model gets about 0.92 on this problem.

How to find it:

  1. Print the training labels: y[:10] are all 0 and y[-10:] are all 2. The rows are sorted by class.
  2. With shuffle=False, each epoch is about 30 batches of class 0, then 30 of class 1, then 30 of class 2. The last updates only teach the model about class 2, so it drifts toward predicting it.
  3. The DataLoader has a setting for the order of visits.

The fix:

loader = to_loader(X, y, batch_size=32, shuffle=True)

Root cause (one line): The training data was sorted by class and not shuffled, so the model kept forgetting earlier classes.

The lesson: Shuffle the training data every epoch. Do not shuffle validation or test data (it is not needed). Also beware of splits that take the "last 20%" of a sorted file.

Case 5: eval mode

What you see: The first evaluation gives 0.347 and the second gives 0.350, for the same model and data. The model reached about 0.91 in training.

How to find it:

  1. Evaluating the same model twice should give the identical number. The change means something random is active.
  2. The model has Dropout (random) and BatchNorm (uses batch statistics in training mode). In training mode both behave differently from evaluation.
  3. Worse, each validation batch holds examples of one class only, so in training mode BatchNorm normalizes with that class as the average, which wrecks the predictions. Training mode even keeps updating BatchNorm's running statistics during evaluation.

The fix:

def evaluate5(model, loader):
    model.eval()                      # switch dropout and batch norm to evaluation behaviour
    correct, n = 0, 0
    with torch.no_grad():             # no gradients needed when only predicting
        for xb, yb in loader:
            pred = model(xb).argmax(1)
            correct += (pred == yb).sum().item()
            n += len(yb)
    return correct / n

Root cause (one line): The model was left in training mode, so dropout and batch norm were active during evaluation.

The lesson: Always call model.eval() before evaluating and torch.no_grad() around it. Remember to call model.train() again before training resumes. A fit() function like the one from Module 3 does this for you.

A sample debugging checklist

Yours will differ, and that is fine. A good checklist is specific and checks the cheap things first.

  1. Print a batch: shapes, value ranges, labels.
  2. Check the order of the data and whether it is shuffled.
  3. Overfit one small batch first.
  4. Compare against a trivial baseline.
  5. Check that train, validation and test share no samples or copies.
  6. Fit scalers and other statistics on the training data only.
  7. Check the loss matches the output (raw logits for CrossEntropyLoss).
  8. Look at the loss values, not only the accuracy.
  9. Try a learning rate range test.
  10. Call model.eval() and torch.no_grad() when evaluating.
